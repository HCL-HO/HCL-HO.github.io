How I build them

  1. Write the requirement first. One page: what it must do, and how I will know it does. No code before that page exists.
  2. Design before code. Screens and a plan are reviewed and approved before anything is built, because a wrong direction is cheap on paper and expensive in code.
  3. One change at a time. Small enough to finish, review and revert on its own — never a batch of five things that must ship together.
  4. Prove it with checks that can fail. A test suite that runs offline and can go red, then the page opened in a real browser: a passing test says nothing about a button that never got wired.
  5. Record the decision. What changed, why, and what proved it, kept beside the code — so the next change starts from evidence instead of memory.
